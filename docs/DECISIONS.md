| 35 | 2026-11-17 | Fork safety: every live `BatchExporter`, `SQLiteStore` and `HttpClient` is reinitialised by `os.register_at_fork(after_in_child=...)`: new lock, events and exporter thread, a new SQLite connection, a new HTTP client. The child starts with an empty queue (the parent still exports spans queued before the fork). Inherited SQLite connections and HTTP clients are kept referenced but never closed. The child's HTTP client is built from a proxy resolved in the parent, with `trust_env=False`. `multiprocessing` children leave through `os._exit`, so the exporter registers a `multiprocessing` finalizer to flush them | Flush the parent's queue in the child; refuse to work after fork; document `tirkit.init()` after fork | Re-exporting the parent's queue would duplicate spans. Closing an inherited SQLite connection can checkpoint or delete the parent's WAL file, and closing an inherited HTTP client can shut down shared sockets. On macOS httpx's system-proxy lookup crashes (SIGSEGV) in a forked child once the parent used it, found by the fork test | NFR-1 |
| 36 | 2026-11-17 | SDK retry policy (Python exporter and TypeScript SDK): retry timeouts, connection errors and HTTP 408, 429, 500, 502, 503, 504; fail other 4xx at once; wait `Retry-After` (plus up to min(1 s, 10%) jitter) when the server sends it, else full-jitter exponential backoff (uniform in `[0, min(5 s, 0.2 s * 2^attempt)]`); give up after 5 retries or 30 s in total, and without sleeping when the wait would pass the 30 s budget. The HTTP client raises `RetryableHTTPError` (with `retry_after`) and the exporter owns the waiting | Fixed doubling delay (previous); retry forever; drop on 429 | Jitter stops many clients that failed together retrying together; honouring `Retry-After` is what lets the server (phase B ingest limits) shed load without data loss. 30 s is longer than a short outage or restart but short enough not to pile up behind a dead server; the queue bound (10,000 spans) still protects the app | NFR-1 |

| 38 | 2026-11-17 | `GET /traces/{id}` returns the light view by default: spans sorted by start time, with 2,000-character previews cut in the database (`substr` of the JSON text, so large inputs never leave it), a paging marker (`total_spans`, `offset`, `omitted`, `next_offset`, default page 10,000, maximum 50,000), and the trace head without the root's input and output. Previews on one page share a budget of 1,000,000 characters, so a 10,000-span trace gets 50 characters per field and stays under 5 MB. `?full=1` keeps the old shape; `GET /traces/{id}/spans/{span_id}` returns one full span. Existing tests that read full spans from the old route now pass `full=1` | Paginate by 500 spans; return no previews; truncate in Python after loading | The plan's "about 2 KB" previews would be 40 MB for a 10,000-span trace, which defeats the light view; the shared budget keeps the default page small and the full span is one click away. String previews are unquoted, other values are the start of their JSON text. Measured with `bench_query.py` (SQLite, 210,000 spans, busy laptop, 20 runs): the 10,000-span light view 101 ms p50 / 176 ms p95 and 5.0 MB, `full=1` 426 ms p50 and 39 MB | NFR-4 |
